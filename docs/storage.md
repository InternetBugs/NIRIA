# 本机资料存储与升级

0.15.0 将数据库 `PRAGMA user_version` 升至 3，沿用原有伴侣实体表，并将整段同步元数据拆成独立记录。备份与同步的伴侣状态仍为 v1，WebDAV 信封和配对码格式不变。服务凭据仍在独立的 Windows 加密配置库，窗口偏好仍在 `desktop.json`。

0.28.0 将凭据库故障与伴侣资料库分开处理。凭据 SQLite 无法打开、结构不兼容或运行时读写失败时，停止本次进程的凭据持久化，不删除或替换原文件；`storage.savedKnown:false` 表示无法核对已存内容，不能由空列表推断“没有配置”。服务状态和本机聊天仍可读取，用户可填写仅本次会话的连接；已存配置重启后仍可能生效，界面持续提示。无法清除时返回明确错误，不报告成功清空。伴侣 SQLite 自身损坏仍按原规则停止打开，不能借此创建新身份。

新服务配置先做无副作用校验，再等待系统加密和凭据写入；成功后同步切换会话连接和配置版本。保存失败不会先替换连接、清零待确认换钥的密钥或丢弃准备方案。凭据存储故障时不启用明文保存；仅系统保护不可用但凭据数据库可用时，仍允许删除已有密文并切换至仅本次会话的配置。凭据表结构、伴侣存储 v3 和备份/同步 v1 未变化。

## 保存内容

| 表 | 内容 | 索引用途 |
| --- | --- | --- |
| `state_meta` | 身份、设置、每日配额、冲突等其余状态 | 单个当前状态 |
| `message_records` | 每条消息的完整 JSON、位置、角色、状态、删除标记和回复关系 | 最近消息、历史分页、对应回复 |
| `memory_records` | 每条记忆的完整 JSON、位置、种类、停用和删除状态 | 当前记忆、分页位置与更新时间 |
| `memory_sources` | 记忆当前有效性依赖的消息、修订号、正文哈希 | 按消息查询衍生记忆；不包含纠正前关联 |
| `deletion_records` | 删除、遗忘与来源 ID 的标记 | 实体 ID 和种类 |
| `call_records` | 有上限的调用记录 | 时间 |
| `avatar_state` | 当前完整形象包 | 独立保存，聊天不重写 |
| `sync_meta` | 小型表头、设备/空间 ID、检查点、换钥标记与各表数量 | 同步存储格式和完整性核对 |
| `sync_records` | 按 `kind:id` 保存各实体的修订图及当前叶节点正文 | 仅更新正文变化的记录 |
| `sync_record_order` | 修订记录的原始顺序 | 排序变化不重写正文 |
| `sync_deletions` | 同步删除标记与位置 | 保留次序及兼容的重复项 |
| `sync_fingerprints` | 每个实体的本机投影摘要 | 仅更新变化的指纹 |

保存比较修改前后的记录，只对新增、修改、删除或位置变化的行执行 SQL。没有修改的形象不会随每次聊天反复写入。单条记忆的来源改变时，来源关系索引也在同一事务中替换。消息和记忆 ID 重复时拒绝整个修改，避免分表时静默覆盖。

0.23.0 在同一 `call_records` 中增加 `kind: "image"` 和四种受支持的 `action`。图片请求开始前原子保存 pending 与每日尝试计数，收到结果为 completed，服务失败为 failed，停止/超时为 unknown；进程重启将遗留 pending 改为 unknown，不重新调用。完成状态无法写入时报告结果不确定，尽可能写入 unknown；持续落盘故障保留 pending，重启再核对。记录只含动作、模型、服务 origin、时间和状态，不保存图片、提示词或密钥。最近最多 500 条，首页显示最后 30 条；图片使用量与现有规则一样保留最多 40 天。

调用记录不进入完整加密备份或同步；原有每日使用量仍随完整备份保存。schema 保持 3，备份/同步仍为 v1；旧版对本机调用种类有白名单检查，因此 0.22.0 及更早版本会拒绝打开含图片调用的新资料库，不能把 schema 相同视为可降级。升级前保留加密备份；日常跨端使用应统一应用版本。

0.24.0 的朗读调用也在上游前保存 pending 和每日 speech 计数，完成/失败/中断更新状态；初始写入失败不提交上游，后续记录失败报告结果不确定，所有路径释放服务忙碌状态。使用量保留最近 40 天，日志不含文本、音频和密钥。恢复时更新进程内 `restoreVersion`，失败事务恢复原标记；它只通过朗读状态的 `historyId` 供页面识别新一轮历史，不写入 SQLite、备份或同步，用于停止旧音频及避免自动朗读恢复的历史。

0.25.0 将相同的调用记录故障区分用于 chat、test、memory、care：初始记录失败不调用模型；完成记录失败尽可能转为 unknown，持续故障保留 pending 等下次启动修复。取消或独立超时也记为 unknown，不把迟到结果标为 completed。聊天和整理结果以伙伴与进程内恢复标记核对，不能写入恢复后的旧调用/回复；失败状态若无法保存则返回存储提示并释放忙碌状态。已有成功回复与完整备份格式保持原规则，后台整理失败不撤销聊天；没有新增持久字段或改变 schema 3/v1。

每条记录仍使用完整 JSON，保留可选表情、上下文引用和兼容字段；形象目前也仍是包含 Base64 图片的完整包，没有做独立资产文件、按帧去重或压缩。删除标记与调用记录按原次序保存，兼容旧备份中可能存在的重复删除标记。

0.31.0 在新回复的 `context.memoryRefs` 中保存可选 SHA-256 `contentHash`，区分记忆正文变化与类型、期限、确认等元数据变化。该字段随原消息 JSON 进入 SQLite、备份和同步，不增加表或改变 v3/v1；恢复前校验摘要格式。没有该字段的旧引用保守核对原完整摘要或修订，因此旧引用在仅元数据变化后也可能退出模型上下文。打开、保存及恢复会按当前引用/来源关系停用旧衍生记忆；模型与同步权限仍分别处理，旧客户端不会执行新保护，应统一升级参与设备。

0.14.0 的形象新增可选 `background: { version: 1, mode: "edge-connected" }`，进入 `avatar_state`、完整加密备份、同步修订及素材包。服务端保存前校验版本、模式和字段，非法设置原子拒绝。没有该字段的 v1 形象继续按原素材显示，不需要迁移数据库；旧客户端可能忽略或在重新保存时丢弃该字段，不能保证旧版显示一致。

背景处理只改变本机显示帧，不覆盖原始 PNG；重新打开按设置重新处理，恢复背景只删除设置。处理后帧不进入资料库、同步对象或备份，避免同时保存两套像素。新动作仍保留生成结果经过等比适配及用户所选对齐的素材；已经发送的透明参考图不能恢复服务从未返回的背景。

事务失败会回滚资料行、来源关系和同步元数据，同时恢复内存中的状态及版本关系。重启时修正中断请求、需要补齐的旧来源哈希及已有遗忘标记遗漏的衍生记录，不重新提交模型请求；打开同步服务时也按当前标记清理已有修订图正文，不自动访问远端。

0.27.0 增加进程内 `stateVersion`：身份、设置、用量、调用记录、形象或任一实体实际变化时更新；无改动的事务不更新，失败的本机事务或同步提交恢复原标记。它与恢复标记及当前同步状态一起形成恢复确认摘要，通过已认证的 `/api/state` 返回；不写入数据库、备份或同步，也不是认证凭据。恢复接口必须提供 `expectedBasis`，解密前后均核对，避免旧备份覆盖确认后新增的本机资料。原有 v1 备份文件仍可恢复，无须修改文件格式。

恢复先在原 SQLite 事务中保存伴侣与同步元数据，成功后才锁定旧同步会话并清除内存密钥；事务失败保留原连接、密钥和自动同步设置。清除已保存配对码发生在提交后，其失败返回成功及独立警告，不撤销或重复恢复。尚在保存配对码或服务配置时拒绝恢复；恢复期间暂停新的同步与配对写入。导出在开始时捕获完整快照，等待加密期间新增的资料留在本机，不混入该次快照。

`core/sync-storage.mjs` 在同一 SQLite 事务中保存表头及各同步表；每行内容相同时跳过更新，完全没有变化的同步元数据不写入。记录正文与顺序分开保存，因此新增消息造成排序变化时，只移动小型位置记录，不重写未变化的形象或旧消息修订图。读取时核对数量、键、位置与表头版本；缺表、缺行、重复顺序或未知版本停止打开，不生成空白同步身份。运行时不缓存落盘基线，避免事务回滚后缓存错误导致漏写。

## 旧库迁移与降级

检测到旧版 `companion` 单行快照后，先验证完整状态，再在一个 SQLite 事务内建立表、写入实体及索引、留下降级保护标记，并设置存储版本。事务失败回滚整个结构和数据；保留原快照，下次可重试。原有 `sync_meta` 不被重建。

0.8.0 至 0.14.0 的实体表库也在一个事务中升级：读取原同步 JSON、拆分记录与顺序、保留指纹/删除/换钥状态、补齐聊天及记忆位置索引，然后更新存储版本和降级保护标记。任一步失败回滚全部新表、旧元数据、版本与保护标记。未配对且没有同步行的资料不会因此创建同步身份。

成功迁移后，原 `companion` 行只保留 `version: 3` 的格式标记，不留下可继续使用的旧正文副本。0.7.0 读取该标记时拒绝打开，0.8.0 至 0.14.0 因较新的数据库版本拒绝打开。较新未知格式、损坏快照、缺失表或保护标记会停止打开，不自动创建另一位空白伴侣。

升级前可在旧版导出完整加密备份并单独保留配对码。新版本支持恢复原 v1 加密备份；如果需要回到旧版，应使用另一个资料目录和升级前的备份。不要让旧版直接使用已经迁移的新库。数据库自身仍未加密；事务和逻辑删除不承诺擦除磁盘、WAL、备份或其他设备的历史副本。

## 窗口读取与历史搜索

主窗口与小窗使用 `/api/state?messages=recent&memories=none`，只从 SQLite 读取最近 120 条未删除消息，并在复制状态前排除完整记忆数组；普通内部快照、备份和同步继续使用完整资料。精简状态带有当前聊天版本、未删除数量与全局最近用户消息 ID，避免历史页把自己的最后一条误认为可编辑消息。`assets=0` 会在复制状态之前排除素材。

`core/message-history.mjs` 提供 `/api/messages` 的 SQL 查询。默认每页 60 条，上限 100 条，按保存的 `position` 双向定位，返回时仍按聊天先后排列；锚点可展开较早来源附近的聊天。未删除的待处理、失败及冲突记录也可查看，冲突记录不开放编辑、重新回复或朗读。

搜索最多 200 个字符，使用参数绑定的 `instr(lower(json_extract(data,'$.content')), lower(?))` 做字串匹配。中文按原文匹配，ASCII 英文不区分大小写，`%`、`_` 和引号都是普通文字。它不分词、不做深层语义检索；会扫描当前消息正文，没有宣称使用全文检索索引。

分页游标绑定伴侣身份、搜索词摘要和当前聊天版本。新增、编辑、删除、重新排序及同步后的消息变化会更新版本；其他设置、调用记录或记忆修改不使聊天游标失效。事务失败时版本回滚，进程重启会生成新版本。失效游标返回 409，界面清除旧页并重新定位；找不到已删除的锚点则回到最近匹配页。游标只是位置编码，不签名，也不作为权限边界；这些接口仍须通过本机 Host、Origin 与会话令牌检查。

历史界面只保留当前页，搜索请求可取消并用请求序号拒绝晚到的旧结果；关闭时清空结果与搜索词。搜索词不保存到数据库或模型请求。记忆来源展开时通过独立接口读取，对每条来源检查状态、冲突、修订和正文哈希，旧来源不可用时只返回提示。

聊天提交接口只返回成功状态，窗口再读取最新的有限消息集合，不在聊天响应中重复返回完整伴侣状态；内部备份与默认资料快照仍保留完整数据。

## 记忆分页、筛选与引用

`core/memory-list.mjs` 提供 `/api/memories`，按保存的记忆位置从新到旧双向读取，默认每页 60 条、上限 100 条。可组合最多 200 字符的本机字串搜索、资料类型与有效状态；字串规则与聊天搜索相同，特殊符号不作为 SQL 通配符。`memories_browse(deleted,position)` 支持无筛选的位置查询，正文和状态筛选仍可能扫描匹配范围，没有全文或语义搜索索引。

“已确认且有效”“待确认”“停用、过期或冲突”使用当前来源、正文哈希、纠正阻止和到期规则判定，不单看保存的确认/停用标记。有效状态缓存在内存中，由 SQLite 标量函数参与筛选；记忆、消息或冲突变化以及期限到达、时钟回拨都会重新计算，不为浏览写入数据库。

`memoryWindow` 摘要含当前版本、未删除总数、各状态数量与最近到期时间。游标绑定身份、搜索及筛选、记忆/来源版本和已跨过的期限，事务失败同时恢复版本；重启后旧游标失效。较早页面编辑后按首条记录重新定位，锚点删除或不再匹配时回到最近匹配页；最新页会接纳新增记录。请求取消、序号校验和离开页面时清空结果，避免显示晚到旧页。搜索与筛选只保留在当前界面，不写入备份或同步。

回复的“引用的记忆”通过 `/api/memories/references` 按需读取，独立于当前页面。接口核对完整回复上下文、回复修订及记忆当时的修订和可用哈希；记忆改变、到期、删除或来源失效时只返回不可用提示。弹窗关闭后取消读取并清除内容，当前版本变化或期限到达时重新核对。这些只读接口同样需要本机会话令牌与 Host/Origin 检查，不请求模型。

## 记忆期限与遗忘清单

记忆的 `kind` 和 `expiresAt` 可以独立编辑。`datetime-local` 输入按当前设备时区转换为 ISO 时间，未改动的日期保留原始秒数；空白或过去日期拒绝保存，长期保留用 `null` 表示。只改元数据不清除来源、不自动确认、不解除停用；正文纠正成为独立手动资料。打开编辑表单时保存原条目，提交以完整原值核对，防止同整数修订的不同正文被旧表单覆盖。

0.11.0 的 `core/memory-provenance.mjs` 区分有效性依赖与纠正前关联。正文实际改变时，原 `sources` 移到可选 `supersededSources`，仅保留 ID、修订及可用的正文哈希；相同正文提交不解除来源或确认状态。纠正前关联不进入 `memory_sources`，仍保存在实体 JSON、备份及同步版本中；条目最多 50 个关联，导入时检查格式和数量。

按当前来源修订/哈希找到被替代消息，再沿 `replyTo` 扩展，模型上下文和自动整理排除这组记录。其他以这些记录为当前来源的记忆会停用，不按语义猜测其中哪些事实已经改变。检查在每轮有效性校验及提交前执行，修改时保存停用状态；纠正条目本身不因旧消息变化而失效。另发的新消息或不同版本仍可提供新资料。

原关联参与模型/同步权限及遗忘清单，普通删除原消息不删除独立纠正；显式遗忘原来源则同时清除相关纠正正文。删除纠正记忆时，必要的版本引用合入删除标记，保证新设备没有该记忆正文时仍能排除旧来源。过期条目的关联也继续生效，避免过期导致旧事实复活。

恢复相同身份时，纠正前的旧记录不能覆盖本机已有纠正；备份已经携带纠正时采用备份正文并合并关联。若本机保留了纠正，同一同步空间还会保留对应记忆的版本关系，再把恢复后的变化观察为后继修订，避免把自己的已知纠正当成并发冲突。恢复到另一身份不携带本机的纠正内容。

这些关联可在来源界面按需读取和校验，界面明确标为原关联记录；不复制被替代正文。旧版本此前丢失的来源关系无法追溯重建，其他独立消息的语义矛盾不在这套规则内。旧客户端会忽略新字段和规则，这项行为需要各设备运行 0.11.0 或更高版本。

`core/forget-preview.mjs` 从本机消息、记忆和已知冲突版本生成清单，包含原始来源、沿 `replyTo` 到达的回复及以这些消息为来源的记忆。混合来源记忆会删除，但其其他独立来源不自动成为遗忘根。没有显式来源关系的手动资料不按相似文字删除。

`/api/memories/forget-preview` 返回各类数量、正文片段、分页位置和计划摘要。每页默认 30 条，最大 100 条；更长聊天可打开历史查看完整内容。摘要绑定伴侣身份、目标、来源关系和所有受影响的当前版本，相关变化时分页及提交返回 409。它用于并发核对，不作为认证凭据；接口仍由本机会话令牌及 Host/Origin 保护。预览不落盘、不请求模型，关闭时清除片段并取消旧读取。当前状态变化时界面重新核对，拒绝显示晚到旧清单。最终 HTTP 遗忘必须提供刚查看清单的摘要。

`core/deletion-cascade.mjs` 在本机删除、重启修复、备份恢复与同步合并中复用规则。普通消息删除沿回复关系传播，衍生记忆停用；显式遗忘把来源和关联回复标记为遗忘，并清空依赖这些消息的记忆正文。遍历使用队列，不受记录顺序影响，循环关系也会终止。较弱的普通删除标记不能覆盖遗忘，删除记忆的来源集合按并集合并，继续阻止旧来源自动重建。旧记录中仍保留的 `replyTo` 和来源 ID 用于发现从未上传或此前已删除的关联记录。

删除、来源索引、聊天版本与同步修订图仍在同一事务中；失败同时回滚。标记只保留 ID、种类、时间和必要来源，不新增被遗忘正文副本。数据库、WAL、加密备份和服务端历史版本仍不保证物理擦除。

## 召回与性能边界

来源有效性检查在每轮召回建立消息 ID 索引，并复用正文哈希，避免每条记忆再扫描全部聊天。0.21.0 将一次性分词缓存改为进程内倒排索引；查询词只访问对应的记忆 ID 集合。有效期、来源修订/哈希、冲突和模型权限仍在每轮选取前检查，只有有效且允许模型使用的正文参与索引与词频计算。

新增聊天、调用记录或修改确认状态等元数据后，未变正文保留分词。保存纠正、撤权、删除、来源失效时立即移除旧词条，新增或改写的正文在下一次非空检索中才分词。时间跨过期限后，下次读取重新清理；时钟回拨也重新检查期限。恢复或同步替换快照、事务失败及关闭资料库会丢弃相应索引；重启按当前有效正文重建。索引不进入 SQLite、加密备份或同步对象，不改存储版本 3 或 v1 协议。

检索仍按本地词语相关性排序，不是 embedding 或深层语义召回。SQL 来源索引已建立并验证查询计划；当前对话召回仍在内存处理，没有将整个模型上下文选择改成 SQL 查询。

`npm run test:recall` 以 20,000 条合成消息、4,000 条有来源记忆比较原扫描算法和倒排索引，逐次断言选取 ID、顺序、原因及字数预算相同。在 `artifacts/recall-benchmark-1794647307963/result.json` 的一次本机诊断中，新增聊天后的召回为原算法约 49.33 ms、索引约 12.68 ms；改写一条后约 48.23 / 18.74 ms。三轮冷启动/修改后的正文分词量由 12,000 次变为 4,001 次，新增聊天为 0、一次改写为 1。热查询有波动，部分短查询没有改善；这些数字不是整体聊天耗时、通用加速保证或实际用户历史测量。该次诊断仍包含完整排序，快照替换后仍会重建索引。

0.30.0 按既有比较规则构建优先堆，只按需要取出候选，最多选取 30 条。有效性和模型权限先于计分检查，所有有效条目继续参与词频；超过初始字数预算的正文只在候选阶段排除。其余候选的长度计数用于判断剩余预算是否还能容纳任何正文，避免预算耗尽后仍排序/弹出全部条目。ID 在本机比较中等价时保持原数组次序，空正文和 UTF-16 字数计算也保留原行为。

诊断脚本现在另保留 0.29.0 的索引加完整排序作为参考，避免把此前分词优化算成本轮收益。`artifacts/recall-benchmark-1794665493494/result.json` 中五类查询共 25 个预热样本交替执行两种算法，整体中位数为完整排序 12.45 ms、当前选取 7.79 ms；逐次选取结果与完整排序、历史扫描都相同，分词次数仍为原扫描 12,000 / 当前 4,001。只是这台电脑的一次合成诊断，部分样本或修改后的查询仍会更慢，冷启动的执行顺序不同，不能作为可比冷启动速度、通用加速保证或实际聊天端到端耗时。

选取仍遍历有效性并构建全部候选；预算跳过可能访问很多条目。大历史的完整状态载入、复制比较和远端整包同步没有因此解决，也没有增加语义检索或外部模型请求。索引、排序临时结构和长度计数均不进入资料库、备份或同步，存储 v3 与备份/同步 v1 不变。

`npm run test:storage` 使用 20,000 条合成消息与 4,000 条有来源记忆，未启用同步，验证迁移、单条追加、旧记忆召回及重启。一次本机测量中，旧 JSON 快照正文为 12,303,164 字节，追加消息只插入一行、正文 224 字节。这个数字不包含 SQLite 页、索引和 WAL 的开销，不是实际磁盘写入总量。

同次诊断记录的迁移约 484 ms、追加约 51 ms、首次召回约 54 ms、再次召回约 22 ms、重开约 154 ms，只代表这台电脑的一次合成运行。旧整段 `UPDATE` 的对照只计序列化和写入，未包含完整应用操作，不能用它推断新旧端到端速度。当前每次修改仍会复制和比较内存状态，启动也仍全量读取；不能据此宣称已经完成大规模性能优化。

0.15.0 已将本机同步元数据改为按记录保存。`npm run test:sync-storage` 使用 2,000 条合成消息、400 条有来源记忆及一张微小测试 PNG，先配对并建立修订，再观察追加一条聊天的 SQLite 触发器。在一次本机运行中，真实 0.14.0 运行代码重写了 2,099,806 字节同步 JSON；新实现新增 500 字节记录正文、64 字节指纹和 427 字节表头，另有 2,376 字节顺序字段，没有更新其他正文，无变化时零写入。证据为 `artifacts/sync-storage-benchmark-1794553251409/result.json` 与 `artifacts/sync-storage-benchmark-1794553251816/result.json`。顺序更新数量会随新 ID 在排序中的位置而变化。

这些数字是触发器统计的 JSON/字段逻辑字节，不是实际磁盘或 WAL 写入量，也不包含索引开销。两个诊断使用同规模但独立的合成记录，耗时不能视为通用速度保证。本机仍会全量载入、复制和比较状态与修订图，每次保存也会逐项序列化/比较；单条记录内部的版本图仍整条保存。聊天和记忆的有限读取已经完成，资产分块、核心增量处理与远端增量同步仍待完成；远端仍上传完整加密对象。

## 验证方法

自动测试覆盖原样迁移、重复打开、迁移写入中断后回滚与重试、未知格式、缺表、未完成请求修复、单行追加、来源关系变化、遗忘后正文清除、同步监听器失败时的回滚，以及旧加密备份恢复。另有带真实修订图冲突的迁移测试，升级后仍可选择版本并与另一客户端收敛。

聊天历史另有 247 条合成消息的双向遍历、字串与特殊符号、锚点、失效游标、编辑/删除/恢复、同步冲突选择、远端删除及来源哈希检查。浏览器覆盖较早来源、并发搜索、嵌套编辑、已删除正文清除、纯文本显示与 390px 布局；实际 Electron 检查双窗口的精简读取和同一套历史/来源界面。所有资料均来自隔离测试，不请求真实模型。

记忆生命周期测试覆盖只读遗忘预览及分页、取消、新衍生/同修订正文变化使旧计划失效、冲突来源并集、缺失来源、无关记录保留、逆序与循环关系、旧加密备份中未知回复、旧不完整标记重启修复、跨端已删除回复的衍生清除、同步元数据回滚、期限/类型独立修改、过期期间正在生成的回复被丢弃，以及 HTTP 确认要求。浏览器和实际 Electron 也验证期限字段、取消与确认清单及无额外模型调用。

记忆纠正新增十四项测试，覆盖版本关联、重复纠正、相同正文、同修订不同哈希、新来源、旧回复链、旧衍生停用、整理前/过程中纠正或撤权、未召回纠正记忆时的旧回复拒绝、权限独立、纠正后的遗忘与关联清除、备份和实际 SQLite 重开、旧备份恢复后的同步版本关系、离线整理、冲突候选、过期/删除后阻止及无效输入。浏览器还复现快速关闭/重开遗忘清单，检查延迟关闭事件不破坏新清单。

`scripts/prepare-storage-upgrade.mjs` 从已验证的 0.7.0 `app.asar` 提取运行代码，以该代码生成隔离的旧库和加密备份。应在重建新包前运行；它不读取用户的实际资料，也不使用真实服务凭据。

`node scripts/desktop-smoke.mjs --packaged --upgrade` 在新包的实际 Windows 进程中打开该旧库，核对身份、全部状态和同步元数据，恢复旧备份、追加消息，再尝试用旧运行代码打开新库并确认被拒绝，最后重新打开新包检查数据、删除和权限仍正确。这个流程验证资料库升级；没有执行安装器安装、卸载或覆盖安装。

新增 14 项同步存储测试覆盖单条追加/无变化写入、重排不改正文、重复删除标记、撤权和遗忘后的实际落盘正文清除、晚阶段指纹失败、远端提交失败、独立事务失败、v2 升级/索引补齐/重复保存、迁移失败回滚重试、未配对升级、无效或未知旧元数据、缺表/缺行/顺序损坏/未知表头、降级保护和实际 SQLite 重开后的换钥标记。

`node scripts/prepare-storage-upgrade.mjs --v2` 只能在已验证的 0.14.0 包仍在 `win-unpacked` 时运行；它从该实际包提取运行代码，准备带背景设置、权限、删除标记与加密备份的 v2 夹具，独立保存到 `artifacts/storage-v2-upgrade-fixture.json`，不覆盖原 0.7.0 夹具。后续使用 `node scripts/desktop-smoke.mjs --packaged --upgrade --upgrade-v2` 验证两条升级路径、旧程序拒绝新库及再次重启。不要用新源码重新生成“旧库”。
